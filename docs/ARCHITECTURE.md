# ARCHITECTURE.md

## Тип ядра

Монолитное. Полное обоснование — `docs/adr/0001-monolithic-kernel.md`.

## Поток загрузки

```
GRUB (Multiboot)
  → boot/boot.S: _start
      настройка стека, push magic/mbi_addr, call kernel_main
  → kernel/kernel.c: kernel_main()
      1. vga_init(), serial_init()      — вывод сразу, до всего остального
      2. проверка Multiboot magic
      3. gdt_init()                      — плоская модель памяти
      4. idt_init()                      — таблица прерываний
      5. isr_init()                      — обработчики исключений CPU
      6. irq_init()                      — remap PIC, диспетчер IRQ
      7. timer_init(), keyboard_init()   — регистрация IRQ-обработчиков
      8. sti                             — включаем прерывания
      9. pmm_init()                      — физическая память по mmap
      10. основной цикл (пока — эхо клавиатуры)
```

Порядок в пункте 3-8 важен: IDT должна существовать до включения
прерываний (sti), а обработчики должны быть зарегистрированы до того,
как реально может прилететь IRQ.

## Прерывания: ISR vs IRQ

Два независимых механизма на одной таблице (IDT):

- **ISR (0-31)** — исключения CPU (деление на 0, page fault и т.д.).
  Процессор вызывает их сам в момент ошибки. У нас все 31 ведут в
  `panic()` — на этом этапе ничего восстанавливаемого (кроме page
  fault, который в Milestone 0.2 получит свою обработку для paging).

- **IRQ (32-47)** — аппаратные прерывания от устройств (таймер,
  клавиатура) через контроллер PIC. PIC физически шлёт IRQ0-15, мы их
  remap'нули на векторы 32-47, чтобы не пересекаться с ISR 0-31
  (дефолтный remap PIC — это классическая OSDev-практика, без него
  IRQ0 будет путаться с исключением "Divide By Zero").

Оба механизма используют одинаковый паттерн: crate ассемблерный
стаб на каждый вектор (`isr.S`/`irq.S`) → сохранение регистров →
вызов общего C-обработчика (`isr_handler`/`irq_handler`) →
восстановление регистров → `iret`.

## Память на этом этапе

Сейчас работает **только физическая** память — PMM (`mm/pmm.c`)
выдаёт свободные страницы по 4 KiB на основе Multiboot memory map.
Виртуальной памяти (paging) ещё нет — весь код и данные ядра сидят
по своим физическим адресам как есть (загружены линкером на 1 MiB,
`arch/i386/linker.ld`). Это Milestone 0.2 — см. ROADMAP.md.

## Драйверы

Каждый драйвер — независимый модуль в `drivers/<name>/`, с чётким
`.h`-интерфейсом. Ни один драйвер не знает о внутренностях другого:
- `vga` и `serial` не знают друг о друге — их объединяет только
  `lib/stdio.c` (`kprintf` пишет в оба)
- `keyboard` и `timer` регистрируются в `irq.c` через
  `irq_install_handler(irq_num, callback)` — irq.c не знает, что
  внутри callback'ов

Это специально: когда дойдём до вынесения драйверов в user-space
(гибридная модель, если решим туда идти) — граница уже есть, менять
не сам код драйвера, а только то, как он регистрируется.

## Почему higher-half kernel — следующий шаг, а не сейчас

Пока ядро грузится по физическому адресу 1 MiB и работает с
идентичным маппингом (virtual == physical, потому что paging
выключен). Как только появится paging (Milestone 0.2), стандартная
практика — переехать на 0xC0000000 (higher half), чтобы нижняя
половина адресного пространства осталась свободной под user-space
процессы в будущем (Milestone 0.5). Делать это сейчас, до paging,
бессмысленно — переезд привязан к включению virtual memory.
