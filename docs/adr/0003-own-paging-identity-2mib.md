# ADR-0003: Свои page tables — identity map, 2 MiB страницы, по EFI memory map

## Статус
Принято

## Контекст

До Milestone 0.4 ядро работало на page tables, оставленных UEFI firmware
до `ExitBootServices()`. Это позволяло дойти до рабочего шелла (milestone
0.3 закрыт, живой бут подтверждён), но это чужая память в неизвестном
формате — прошивка не обязана сохранять её содержимое или структуру, это
просто исторически сработало. Первый шаг Milestone 0.4 ("memoria") —
завести собственные таблицы, на которые ядро полагается осознанно.

## Решение

- Строим свои PML4/PDPT/PD (`mm/paging.c`), без PT (нет 4 KiB-страниц).
- Гранулярность — 2 MiB страницы (PS-бит в PD-entry), не 4 KiB.
- Схема адресации — **identity map** (виртуальный адрес == физический),
  та же модель, что была у прошивки. Higher-half — не в этом шаге.
- Диапазон покрытия строится в три слоя:
  1. Безусловно — первые `BASE_IDENTITY_GIB` (4) GiB, статически
     выделенными PD-таблицами (без изменений скомпилировано с
     фиксированным размером — свободного `kmalloc` ещё нет).
  2. Каждый регион из настоящей EFI memory map (`nexus_boot_info_t.mmap`)
     — включая MMIO/reserved/ACPI, не только "нашу" RAM, т.к. неясно,
     что именно тронет код ядра или сама CPU по пути.
  3. Framebuffer явно (`nexus_boot_info_t.fb`) — он приходит из GOP,
     а не гарантированно из memory map тем же адресом/типом, и дырка
     тут означала бы page fault на первой же попытке что-то напечатать
     сразу после переключения CR3.
- Регионы выше `BASE_IDENTITY_GIB` (в основном framebuffer на некоторых
  машинах) получают PD-таблицу из небольшого статического пула
  (`EXTRA_PD_SLOTS = 8`) — best-effort: если пул когда-нибудь кончится,
  паджинг молча пропускает страницу вместо паники (см. `pd_table_for()`).
  На практике framebuffer — один 1 GiB слот, пул с большим запасом.
- PAE и long mode уже включены прошивкой до прыжка в `kmain` — не
  трогаем их заново, только строим новые таблицы и делаем `mov cr3`.

## Альтернативы, которые рассматривали

- **4 KiB страницы сразу.** Отклонено пока: больше таблиц, больше кода,
  а честной причины дробить мельче 2 MiB ещё нет — ни свопинга, ни
  защиты отдельных 4 KiB регионов друг от друга (весь код — кольцо 0).
  Если понадобится (например под `kmalloc`/heap) — отдельный ADR.
- **Higher-half kernel сразу вместе с paging.** Отклонено: две разные
  задачи в одном шаге (риск сложнее диагностировать, если что-то не
  бутится). ROADMAP уже держит higher-half отдельным пунктом Milestone
  0.4, ближе к user/kernel split (Milestone 0.6).
- **Мапить только то, что реально нужно (lazy/on-demand), а не всю
  memory map целиком.** Отклонено: без page fault handler'а с реальным
  demand-paging (которого пока нет — только диагностика) это просто
  создало бы неотличимые от бага дыры. Мапить всё, что описала
  прошивка, — не самый экономный вариант, но самый предсказуемый.

## Последствия

- Ядро больше не зависит от таблиц, оставленных UEFI — сборка теперь
  "самодостаточна" в этом смысле.
- Готовит почву под `kmalloc`/`kfree` (Milestone 0.4, следующий шаг):
  физическая memory map уже читается (`kstate_mem_summary()`), paging
  уже умеет отображать произвольные физические диапазоны.
- Не решает и не блокирует: page protection (защита кода от записи,
  NX для данных) — пока PTE_WRITABLE стоит везде, включая .text.
  Разделение прав по секциям (`.text` read+exec, `.rodata` read-only,
  `.data`/`.bss` read+write) — не сделано в этом шаге, отдельная задача
  (не заведена как отдельный пункт ROADMAP пока, стоит добавить, если
  до неё дойдут руки раньше "descent").
- Диагностика: `meminfo` (шелл) показывает CR3 и охваченный диапазон;
  page fault (vector 14) теперь расшифровывает CR2 и биты error code
  вместо голого "unknown exception".
