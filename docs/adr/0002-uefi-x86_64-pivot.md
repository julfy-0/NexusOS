# ADR-0002: Пивот на UEFI/x86_64 вместо BIOS+GRUB Multiboot/i386

## Статус
Принято. Заменяет фактическую реализацию из Milestone 0.1-0.2 (ADR-0001
про монолитное ядро остаётся в силе — это ортогональное решение).

## Контекст
Собственная BIOS+GRUB+Multiboot+i386-реализация (genesis, версии
0.1.0-0.1.2) упёрлась в трудноуловимый баг линковки/GRUB
("no multiboot header found"), а сборка требовала болезненной
самостоятельной компиляции кросс-компилятора `i686-elf-gcc`
(10-20 минут, куча зависимостей).

У пользователя уже существовал отдельный, более старый и куда более
развитый проект: собственный UEFI-загрузчик (PE32+, парсит ELF64 сам,
без GRUB), 64-битное ядро в long mode, GDT/IDT/ISR под x86_64, PIC/PIT,
консоль на линейном framebuffer (через UEFI GOP), PS/2-клавиатура,
AHCI+PCI+FAT32, и встроенный (в контексте ядра) шелл с ~50 командами.
По словам пользователя, этот вариант реально грузился.

## Решение
Полностью заменить архитектуру: BIOS/i386/GRUB → UEFI/x86_64/свой
загрузчик. Весь код перенесён из старого проекта пользователя в текущую
структуру каталогов (`arch/`, `boot/`, `drivers/`, `kernel/`, `fs/`,
`lib/`) практически без изменения логики — только реорганизация путей.
Подробное соответствие старых путей новым — в `docs/MIGRATION_0002.md`.

Ключевое практическое следствие: **кросс-компилятор больше не нужен**.
UEFI-приложение — это PE32+ x86-64, ядро — ELF64 x86-64; если разработка
идёт на x86_64 Linux, обычный `gcc`/`ld` хоста собирает оба бинарника
напрямую (`-m i386pep` для PE32+ поддерживается стоковым `binutils`).
Это единственная причина, по которой предыдущая ветка требовала
toolchain/build-cross-compiler.sh, и теперь этот скрипт удалён как
неприменимый.

## Альтернативы, которые рассматривали
- **Доломать баг в BIOS/GRUB-версии и продолжить с ней** — отклонено:
  у пользователя уже был рабочий (по его словам) альтернативный вариант,
  объективно более развитый (long mode, framebuffer, диск, FAT32,
  50 команд шелла против нашего эхо клавиатуры). Чинить менее развитую
  и не подтверждённую версию не было смысла, когда есть более развитая
  и (предположительно) рабочая.
- **Держать обе ветки параллельно** (BIOS для legacy-железа, UEFI для
  современного) — отклонено на данном этапе: усложняет всё (два
  загрузчика, два набора arch-кода) без практической необходимости —
  современные машины и QEMU одинаково поддерживают UEFI.

## Последствия
- Реальная сборка **проверена в этой же сессии** конечным
  тулчейном (`gcc`/`ld` хоста, не sanity-check): и `BOOTX64.EFI`
  (PE32+, EFI application, x86-64), и `kernel.elf` (ELF64, entry
  0x200000 — совпадает с `arch/x86_64/linker.ld`) слинковались без
  единого warning'а. Живой бут в QEMU+OVMF всё равно не проверен —
  в песочнице разработки нет `qemu-system-x86_64`/OVMF/`mkfs.vfat`.
- Milestone-структура ROADMAP.md больше не описывает реальный порядок
  разработки — старый проект уже принёс с собой куски "archive"
  (AHCI+FAT32) до того, как появилась honest paging ("memoria") или
  многозадачность ("threadwork"). ROADMAP.md переписан, чтобы отражать
  фактическое состояние, а не воображаемую линейную последовательность.
- Шелл и все 50 команд работают **в контексте ядра** (вызываются прямо
  из обработчика прерывания клавиатуры), не как user-space процессы.
  Переход в ring 3 (Milestone "descent") остаётся не сделанным и теперь
  требует вынести уже работающий шелл из kernel-context в отдельный
  процесс — это отдельная будущая работа, не бесплатная.
- `docs/adr/0001-monolithic-kernel.md` не отменяется: новая архитектура
  тоже монолитная (шелл и все драйверы в кольце 0).
